## Remaining concrete caveat: score inputs are absent from the resume fingerprint

`scripts/stage3_extension.py` fingerprints its own code, measure code, CSV reader, cohort metadata, stage-0 table and split labels. It does **not** fingerprint `analysis_submissions.parquet`, raw `Submissions.csv`, or a run manifest linking those score inputs to this cache.

Thus a score-only change preserving counts, metadata and labels can leave the fingerprint unchanged. If the Parquet extract is replaced while the row store remains, the script can reuse previously measured rows. If raw data change while the Parquet file remains, extraction itself is skipped. The run-start manifest records raw hashes but the stage-3 resume guard does not consult them.

**Fix:** bind both extraction and row-store caches to the relevant raw-input/code fingerprint, or explicitly restrict resume to unchanged score inputs and require CLEAN when they change. The description should say what is actually checked rather than “any changed code or inputs.” Full Parquet content hashing is not the only solution: provenance linking the extract to validated raw hashes can suffice in this controlled workflow.

This is not evidence that a stale cache contaminated either final run. Their fresh-run provenance and matching retained outputs are reassuring; the concern is future non-clean reuse and the breadth of the safety claim.
